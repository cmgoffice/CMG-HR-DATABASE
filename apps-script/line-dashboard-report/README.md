# ส่งสรุปรายงาน Dashboard เข้ากลุ่มไลน์ ผ่าน LINE OA (Google Apps Script)

โค้ดในโฟลเดอร์นี้ (`Code.gs`, `appsscript.json`) เป็น Google Apps Script project ที่:

1. อ่านข้อมูลจาก Firestore ของระบบ CMG-HR-DATABASE (collections: `employee_data`, `employee_follow_ups`, `day_offs`)
2. สรุปเป็นข้อความรายงาน
3. ส่งเข้ากลุ่มไลน์ผ่าน LINE Messaging API (Push Message)
4. รันอัตโนมัติทุกวันตามเวลาที่ตั้งไว้ (time-driven trigger)

ไฟล์เหล่านี้เป็น **ซอร์สโค้ดอ้างอิง** เท่านั้น ต้องคัดลอกไปวางใน Apps Script project จริงที่ https://script.google.com (Apps Script รันแยกจาก React app ไม่ได้ deploy ไปพร้อมกับ `npm run build`)

---

## ขั้นตอนที่ 1: สร้าง LINE Official Account + เปิด Messaging API

1. ไปที่ [LINE Developers Console](https://developers.line.biz/console/) แล้วสร้าง **Provider** (ถ้ายังไม่มี)
2. สร้าง **Channel** ประเภท **Messaging API**
3. ในหน้า Channel > แท็บ **Messaging API**:
   - กด **Issue** เพื่อสร้าง **Channel access token (long-lived)** → คัดลอกเก็บไว้
   - ปิด **Auto-reply messages** และ **Greeting messages** (ไม่จำเป็นสำหรับ bot แจ้งเตือน)
4. สแกน QR Code ของ OA เพื่อเพิ่มเป็นเพื่อน แล้ว **เชิญ OA เข้ากลุ่มไลน์** ที่ต้องการส่งรายงาน (เหมือนเชิญเพื่อนเข้ากลุ่มปกติ)

## ขั้นตอนที่ 2: หา groupId ของกลุ่มไลน์

> ⚠️ **ข้อจำกัดสำคัญที่ค้นพบ**: Google Apps Script Web App (`/exec`) จะตอบกลับด้วย **HTTP 302 เสมอ** (redirect ไปยัง URL ชั่วคราวที่ `script.googleusercontent.com`) ทั้งตอน GET และ POST — นี่เป็นพฤติกรรมมาตรฐานของ Apps Script ทุกตัว แก้จากการตั้งค่าไม่ได้ เบราว์เซอร์ปกติจะ follow redirect ให้อัตโนมัติจึงดูเหมือนใช้งานได้ปกติ แต่ **LINE จะตรวจสอบสถานะ HTTP ตรงๆ ไม่ follow redirect** จึงทำให้ **Verify ไม่ผ่าน (เจอ 302 Found)** เสมอ ไม่ว่าจะตั้งค่า deployment ถูกแค่ไหนก็ตาม
>
> ข่าวดีคือปัญหานี้กระทบแค่ "ขาเข้า" (LINE เรียกเข้า Apps Script) ซึ่งใช้แค่ครั้งเดียวตอนหา groupId เท่านั้น ส่วนการทำงานหลัก (Apps Script เรียกออกไปหา LINE เพื่อ push ข้อความ) **ไม่เจอปัญหานี้เลย** เพราะเป็นคนละทิศทาง — ฟังก์ชัน `doPost`/`doGet` ใน `Code.gs` จึงเก็บไว้เป็นข้อมูลอ้างอิงเฉยๆ ให้ **ใช้วิธีด้านล่างแทน** ในการหา groupId

### ใช้ webhook.site หา groupId (แนะนำ ใช้ได้จริง)

1. เปิด https://webhook.site จะได้ URL เฉพาะของคุณทันที (ไม่ต้องสมัคร) เช่น `https://webhook.site/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`
2. ไปที่ LINE Developers Console > Channel ของคุณ > แท็บ **Messaging API** > ช่อง **Webhook URL** → วาง URL จากข้อ 1 แล้วกด **Update** > **Verify** (ควรขึ้น **Success** ทันที เพราะ webhook.site ตอบ 200 ตรงๆ ไม่มี redirect)
3. เปิดสวิตช์ **Use webhook** ให้เป็น ON
4. ไปที่กลุ่มไลน์ที่เชิญ OA เข้าไปแล้ว พิมพ์ข้อความอะไรก็ได้ เช่น "test"
5. กลับมาที่หน้า webhook.site (เปิดค้างไว้) จะเห็น request ใหม่เด้งเข้ามาทางซ้าย คลิกดู → แท็บ **JSON** หรือ **Content** จะเห็นโครงสร้างแบบนี้:
   ```json
   {
     "events": [
       {
         "type": "message",
         "source": { "type": "group", "groupId": "Cxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" },
         "message": { "type": "text", "text": "test" }
       }
     ]
   }
   ```
6. คัดลอกค่า `groupId` (ขึ้นต้นด้วย `C`) ไปใส่เป็น `LINE_GROUP_ID` ใน Script Properties ของ Apps Script (ขั้นตอนที่ 4)
7. กลับไปที่ LINE Developers Console แล้ว **ปิดสวิตช์ Use webhook** กลับเป็น OFF (ไม่จำเป็นต้องใช้ webhook ต่อแล้ว เพราะต่อไปนี้ใช้แค่ push message ขาออกอย่างเดียว)

## ขั้นตอนที่ 3: สร้าง Service Account สำหรับอ่าน Firestore

1. ไปที่ [Google Cloud Console](https://console.cloud.google.com/) เลือกโปรเจกต์เดียวกับ Firebase (`cmg-hr-database`)
2. ไปที่ **IAM & Admin > Service Accounts** > **Create Service Account**
   - ตั้งชื่อ เช่น `line-dashboard-reporter`
   - Role: **Cloud Datastore Viewer** (แนะนำ เพราะอ่านได้อย่างเดียว ปลอดภัยกว่า) หรือ **Cloud Datastore User** ก็ได้ถ้าหา Viewer ไม่เจอ
   - หมายเหตุ: OAuth scope ที่โค้ดขอคือ `https://www.googleapis.com/auth/datastore` (scope เต็ม เพราะ Firestore API ไม่มี scope `.readonly` แยกต่างหาก) แต่สิทธิ์จริงที่ทำได้ถูกจำกัดด้วย **IAM Role** ที่ตั้งไว้ตรงนี้อีกที ถ้าตั้ง Role เป็น Viewer ก็จะอ่านได้อย่างเดียวแม้ scope จะกว้างก็ตาม
3. เปิด Service Account ที่สร้าง > แท็บ **Keys** > **Add Key > Create new key** > เลือก **JSON** → ไฟล์ JSON จะดาวน์โหลดมา เก็บให้ปลอดภัย (ห้าม commit เข้า git)
4. เปิดไฟล์ JSON จะเจอ:
   - `client_email` → ใช้เป็น `SERVICE_ACCOUNT_EMAIL`
   - `private_key` → ใช้เป็น `SERVICE_ACCOUNT_PRIVATE_KEY`

> ⚠️ ตรวจสอบ Firestore Security Rules ว่าไม่ได้บล็อก service account (ปกติ service account เรียกผ่าน Admin SDK/REST API ด้วย OAuth token จะ**ข้าม Firestore Security Rules ได้เลย** ถ้า role IAM ถูกต้อง เพราะเป็นการเข้าถึงแบบ server-to-server ไม่ใช่ client SDK)

## ขั้นตอนที่ 4: สร้าง Apps Script Project

1. ไปที่ https://script.google.com > **New project**
2. ตั้งชื่อโปรเจกต์ เช่น "CMG HR Dashboard LINE Report"
3. ลบโค้ดเริ่มต้นใน `Code.gs` ออก แล้ววางโค้ดจากไฟล์ [`Code.gs`](./Code.gs) ในโฟลเดอร์นี้แทน
4. ไปที่ **Project Settings** (ไอคอนเฟือง) > เลื่อนลงไปที่ **Script Properties** > **Add script property** ใส่ค่าทีละตัว:

   | Property | Value |
   |---|---|
   | `FIRESTORE_PROJECT_ID` | `cmg-hr-database` |
   | `SERVICE_ACCOUNT_EMAIL` | (จาก JSON key ขั้นตอนที่ 3) |
   | `SERVICE_ACCOUNT_PRIVATE_KEY` | (จาก JSON key ขั้นตอนที่ 3 ทั้งก้อน รวม `-----BEGIN PRIVATE KEY-----` ด้วย) |
   | `LINE_CHANNEL_ACCESS_TOKEN` | (จากขั้นตอนที่ 1) |
   | `LINE_GROUP_ID` | (จากขั้นตอนที่ 2) |

## ขั้นตอนที่ 5: ทดสอบ

1. ใน Apps Script editor เลือกฟังก์ชัน `testSendMessage` จาก dropdown ด้านบน > กด **Run**
2. ครั้งแรกจะมีหน้าต่างขอ **Authorize** สิทธิ์การเข้าถึง (UrlFetchApp ฯลฯ) → กดอนุญาต
3. เช็กในกลุ่มไลน์ว่ามีข้อความ "✅ ทดสอบการเชื่อมต่อ..." เข้ามาหรือไม่
4. ถ้าสำเร็จ ให้ลองรันฟังก์ชัน `previewDailyDashboardReport` แล้วดูผลลัพธ์ใน **Execution log** (View > Logs) เพื่อตรวจสอบว่าข้อมูลสรุปถูกต้องตรงกับ Dashboard จริง (ปรับชื่อฟิลด์ใน `computeDailyDashboardData_()` ถ้า schema ต่างจากที่สมมติไว้)
5. เมื่อพอใจกับรูปแบบการ์ดแล้ว รันฟังก์ชัน `sendDailyDashboardReport` เพื่อทดสอบส่งจริงเต็มรูปแบบ (หรือ `testSendDailyDashboardCard` เพื่อส่งแค่การ์ดเดี่ยวๆ ทดสอบก่อน)

## ขั้นตอนที่ 6: ตั้งเวลาให้รันอัตโนมัติ

รันฟังก์ชัน **`createAllDailyTriggers`** ครั้งเดียวจาก Editor จะสร้าง time-driven trigger ให้ทั้ง 2 รายงาน (`sendDailyDashboardReport` และ `sendProjectAttendanceReport`) ส่งอัตโนมัติทุกวันเวลา **10:00 น.** ตามเวลาไทย

ถ้าต้องการตั้งแค่รายงานเดียว ใช้ `createDailyTrigger` (ภาพรวม) หรือ `createProjectAttendanceTrigger` (แยกโครงการ) แยกกันได้

ปรับเวลาที่ต้องการส่งได้ที่ตัวแปร `DAILY_REPORT_HOUR` ด้านบนของ `Code.gs` (ค่าเป็นชั่วโมงแบบ 24 ชม. เช่น `10` = 10 โมงเช้า) แล้วรัน `createAllDailyTriggers` ใหม่อีกครั้งเพื่ออัปเดต trigger เดิม (ฟังก์ชันนี้ลบ trigger เก่าของฟังก์ชันเดียวกันให้อัตโนมัติ ไม่ต้องลบเองก่อน)

ตรวจสอบได้ที่เมนู **Triggers** (ไอคอนนาฬิกาด้านซ้าย) ว่ามี trigger ถูกสร้างขึ้นจริง

## โควต้าข้อความ: ไม่เกิน 300 ข้อความ/เดือน

ปรับให้ระบบส่งข้อความ**น้อยที่สุดเท่าที่จำเป็น** แล้ว เพื่อไม่ให้เกินโควต้ารายเดือนที่ตั้งไว้:

| รายงาน | ปกติ (ไม่มีปัญหา) | ปกติ (มีปัญหา) | กรณีพิเศษ (ปัญหาเยอะมาก) |
|---|---|---|---|
| ภาพรวม (`sendDailyDashboardReport`) | **1 ข้อความ** (Flex card เดียว รวมเคสติดตามไว้ในการ์ดแล้ว) | เหมือนกัน | เหมือนกัน (การ์ดเดียวเสมอ) |
| แยกตามโครงการ (`sendProjectAttendanceReport`) | **1 ข้อความ** (text สั้นๆ "มาครบทุกโครงการ") | **1 ข้อความ** (Flex Carousel ใบแรกเป็นการ์ดสรุปภาพรวม ตามด้วยการ์ดโครงการที่มีปัญหา) | มากกว่า 1 ข้อความ ถ้าโครงการมีปัญหาเกิน 11 โครงการ/วัน (เพราะ carousel ใส่ได้สูงสุด 12 การ์ด/ข้อความ รวมการ์ดสรุป 1 ใบ) |

**รวมแล้วปกติจะอยู่ที่ 2 ข้อความ/วัน** → ประมาณ **60 ข้อความ/เดือน** (เผื่อไว้สำหรับทดสอบด้วยมือเพิ่มเติมได้สบายๆ ภายใน 300 ข้อความ/เดือน)

### ตัวกันเกินโควต้าอัตโนมัติ (safety net)

มีตัวนับข้อความสะสมต่อเดือนอยู่ใน Script Properties (คีย์ `LINE_MSG_COUNT_YYYYMM` รีเซ็ตอัตโนมัติทุกเดือน) ทุกครั้งที่จะ push ข้อความ ระบบจะเช็กก่อนว่าส่งแล้วจะเกิน **`MONTHLY_MESSAGE_LIMIT`** (ตั้งไว้ `300` ในบรรทัดต้นๆ ของฟังก์ชัน `sendLinePushMessages_`) หรือไม่ ถ้าเกินจะ**ไม่ส่ง**ข้อความชุดนั้นเลย (log คำเตือนไว้แทนใน Execution log กันไม่ให้ trigger error)

- รันฟังก์ชัน **`getMonthlyMessageUsage()`** เพื่อเช็กว่าเดือนนี้ส่งไปแล้วกี่ข้อความ
- ปรับเพดานได้ที่ตัวแปร `MONTHLY_MESSAGE_LIMIT` ใน `Code.gs` (เช่นถ้าใช้แพ็กเกจฟรีของ LINE OA ที่จำกัด 200 ข้อความ/เดือน ก็ปรับเป็น `200` ได้)
- รันฟังก์ชัน **`resetMonthlyMessageQuota()`** ถ้าต้องการรีเซ็ตตัวนับของเดือนปัจจุบันเอง (ปกติไม่จำเป็น เพราะขึ้นเดือนใหม่จะเริ่มนับ 0 ใหม่อัตโนมัติอยู่แล้ว)

> ⚠️ หมายเหตุ: การรัน `testSendDailyDashboardCard`, `testSendFirstProjectFlexCard` หรือ `testSendMessage` เพื่อทดสอบ ก็นับรวมในโควต้านี้ด้วย (ยกเว้น `testSendMessage` ซึ่งส่งผ่านอีกฟังก์ชันหนึ่ง `sendLineMessage_` ที่ไม่ผ่านตัวนับ เพราะใช้แค่ตอน setup ครั้งแรกเท่านั้น)

### "กราฟ" ใน Flex Card ทำยังไง (ไม่มี image/chart จริง)

LINE Flex Message ไม่มี chart component ในตัว เลยใช้ 2 เทคนิคแทน (ไม่ต้องพึ่งบริการสร้างภาพภายนอกเลย ฟรี 100% ไม่มี network call เพิ่ม):

1. **Bar chart (แท่งกราฟ)** — ใช้ box 2 อันซ้อนกันแบ่งสัดส่วนด้วย `flex` ratio (อันที่ 1 ใส่สี = ความยาวแท่ง, อันที่ 2 สีเทา = พื้นที่ว่างที่เหลือ) ฟังก์ชัน `buildFlexBarRow_()` ใช้เทคนิคนี้กับทั้ง **OT สะสมรายคน** และ **โครงการที่มีปัญหาเยอะสุด**
2. **Sparkline (กราฟเส้นแบบย่อ)** — ใช้ unicode block characters (`▁▂▃▄▅▆▇█`) ต่อกัน 1 บรรทัด แทนกราฟเส้นแนวโน้ม 7 วันล่าสุด ฟังก์ชัน `computeAttendanceTrend_()` คำนวณ + แปลงเป็น sparkline string

### ฟังก์ชันที่เกี่ยวข้อง

- `computeDailyDashboardData_()` — ดึง + คำนวณข้อมูลทั้งหมด (ใช้ร่วมกับทั้งเวอร์ชัน text และ Flex)
- `buildDailyDashboardFlexMessage_(data)` — สร้าง Flex card (ปรับ field/สี/layout ได้ตรงนี้)
- `computeOtBurdenData_(activeEmployees)` — รวม OT สะสมตั้งแต่ต้นเดือนถึงวันนี้ของทุกคน แล้วคืน Top N คนที่เยอะสุด (ปรับจำนวนที่ `OT_BURDEN_TOP_N`, ปรับสีตามเพดานที่ `OT_MONTHLY_TIERS`)
- `computeAttendanceTrend_(activeEmployees)` — คำนวณ % มาทำงานย้อนหลัง N วัน (ปรับจำนวนวันที่ `ATTENDANCE_TREND_DAYS`) แล้วแปลงเป็น sparkline
- `buildFlexBarRow_(label, valueText, ratio, color)` — ฟังก์ชันกลางสร้าง 1 แถว bar chart ใน Flex (ใช้ร่วมกับทั้ง OT และโครงการเปรียบเทียบ)
- `buildFollowUpFlexSection_(data)` — สร้างส่วนรายชื่อเคสติดตาม (จำกัด 5 รายการ) ฝังในการ์ดเดียวกัน
- `buildFollowUpListText_(data)` — เวอร์ชัน text ของรายการเคสติดตาม (ใช้กับ `buildDailyReportMessage_()` เท่านั้น ไม่ได้ใช้ส่งจริงแล้ว)
- `buildDailyReportMessage_()` — เวอร์ชัน **text ล้วน** เดิม ยังเก็บไว้เผื่ออยากดู/ใช้งาน (ไม่ได้ถูกเรียกใช้ใน `sendDailyDashboardReport` แล้ว)

### ทดสอบก่อนส่งจริง

- `previewDailyDashboardReport` — log JSON ของการ์ด (ข้อความเดียวจริง ไม่มีแยก) ถ้า JSON ยาวเกินจน log ตัดทิ้ง ให้ใช้ `previewProjectAttendanceReportToDoc` ซึ่งรวมการ์ดภาพรวมไว้ในไฟล์ Doc ให้แล้วเช่นกัน
- `testSendDailyDashboardCard` — ส่งการ์ดจริงเข้ากลุ่มไลน์เลย (วิธีทดสอบที่น่าเชื่อถือที่สุด)

## รายงานที่ 2: สรุปการมา/ขาด/ลา แยกตามโครงการ (Flex Carousel)

นอกจาก `sendDailyDashboardReport` (สรุปภาพรวมทั้งบริษัท แบบ Flex card) แล้ว มีอีกฟังก์ชันคือ **`sendProjectAttendanceReport`** ที่แยกรายงานเป็นรายโครงการ:

- **ถ้าวันนี้ทุกโครงการมาครบ (ไม่มีคนขาด/ลาเลย)**: ส่งแค่ **ข้อความ text สั้นๆ 1 ข้อความ** บอกว่ามาครบกี่โครงการ
- **ถ้ามีโครงการที่มีปัญหา**: ส่งเป็น **Flex Carousel** โดย**การ์ดใบแรกสุด**คือ "การ์ดสรุปภาพรวม" (จำนวนโครงการมาครบ/มีปัญหา + ยอดรวมทั้งหมด มา/ขาด/ลา) ตามด้วยการ์ด 1 การ์ด/1 โครงการ (เฉพาะโครงการที่มีคนขาดหรือลา) เลื่อนซ้าย-ขวาดูได้ในแชทเดียว — **รวมเป็น 1 ข้อความเดียว** (ไม่แยกส่งข้อความสรุป text ต่างหากแบบเดิมแล้ว เพื่อประหยัดโควต้า)

### เรื่องค่าใช้จ่าย

Flex Message **ไม่เสียเงินเพิ่ม**จาก text message — LINE คิดเงินจาก "จำนวนข้อความ" เท่ากันทุกประเภท และ **Carousel 1 ข้อความใส่ได้สูงสุด 12 การ์ด** จึงอาจประหยัดโควต้ากว่าการส่ง text หลายข้อความแยกกันด้วยซ้ำ

### แต่ละการ์ดแสดงอะไรบ้าง

- หัวการ์ด: ชื่อโครงการ (พื้นหลังสีแดงถ้ามีคนขาด, สีส้มถ้ามีแต่คนลา)
- จำนวนทั้งหมด / มา / ขาด / ลา ของโครงการนั้น
- สัดส่วนกำลังคน: DC (ไทย/ต่างชาติ) และ Supply (ไทย/ต่างชาติ)
- รายชื่อคนขาด/ลา **เฉพาะกลุ่มงาน Staff** (ดึงจาก field `ตำแหน่ง` ต่อท้ายชื่อ) — ส่วนแรงงาน (worker/supply/sub) นับรวมเป็นจำนวนอย่างเดียว ไม่แสดงชื่อ (บรรทัด "+ แรงงาน N คน (ไม่แสดงรายชื่อ)")
- ถ้ารายชื่อยาวเกิน 8 คน จะตัดแสดงแค่ 8 คนแรก ที่เหลือสรุปเป็น "... และอีก N คน" (กันการ์ดยาวเกินไป)
- **แผนก/ตำแหน่งที่มีปัญหา** (ท้ายการ์ด) — จัดกลุ่มพนักงานในโครงการตาม field `แผนก` (เหมือนตาราง "ตำแหน่งหลักในโครงการ" บน Dashboard จริง) แล้วแสดงเฉพาะแผนกที่มีคนขาด/ลา พร้อมจำนวนตำแหน่ง (`ตำแหน่ง`) ที่แตกต่างกันในแผนกนั้น
  - 🔴 **ไฮไลต์พิเศษ**: ถ้าแผนกไหน "ขาดครบทั้งแผนก" (พนักงานในแผนกนั้นไม่มาเลยสักคน) จะขึ้นบรรทัดสีแดงเด่น "🔴 ชื่อแผนก — ขาดครบทั้งแผนก (N/N คน)" แยกจากแผนกอื่นที่ขาดบางส่วน
  - จำกัดแสดงสูงสุด 6 แผนกแรก (เรียงแผนกที่ขาดครบทั้งแผนกมาก่อน แล้วค่อยเรียงตามจำนวนปัญหามาก→น้อย) ที่เหลือสรุปเป็น "... และอีก N แผนกที่มีปัญหา"

### ถ้าวันนี้มาครบทุกโครงการ: ข้อความ text สั้นๆ 1 ข้อความ

```
📊 รายงานประจำวัน 08/10/2026
แยกตามโครงการ
------------------------------
✅ โครงการมาครบทุกคน: 12 โครงการ
🔎 โครงการที่มีคนขาด/ลา: 0 โครงการ
------------------------------
รวมทั้งหมด: 527 คน | มา 527 | ขาด 0 | ลา 0
```

### ถ้าโครงการที่มีปัญหาเกิน 11 โครงการในวันเดียว

Carousel ใส่ได้สูงสุด 12 การ์ด/ข้อความ และการ์ดใบแรกถูกใช้เป็นการ์ดสรุปภาพรวมไปแล้ว 1 ใบ ดังนั้นถ้าโครงการมีปัญหาเกิน **11 โครงการ** จะถูกแบ่งเป็นหลาย Carousel (หลายข้อความ) อัตโนมัติ โดย `altText` ของแต่ละชุดจะบอกว่าเป็น "ชุดที่ N/M" (altText คือข้อความสำรองที่ขึ้นในแจ้งเตือน/อุปกรณ์ที่ไม่รองรับ Flex) — กรณีนี้จะกินโควต้าเพิ่มเป็นหลายข้อความ/วัน ควรระวังถ้าใกล้โควต้ารายเดือน

### ทดสอบ / ปรับแต่งการ์ดก่อนส่งจริง

- รัน **`previewProjectAttendanceReport`** จะ log ข้อความสรุป (text) + JSON ของแต่ละ Flex Carousel ให้ดูก่อนส่งจริง
  - ⚠️ **ถ้าโครงการที่มีปัญหาเยอะ** JSON อาจยาวจน Execution log ตัดทิ้ง (ขึ้น "Logging output too large. Truncating output.") ทำให้คัดลอกไปวางที่ไหนแล้ว invalid JSON เพราะ JSON ไม่ครบ ให้ใช้ **`previewProjectAttendanceReportToDoc`** แทน (ดูหัวข้อถัดไป)
- ปรับรูปแบบการ์ดได้ที่ฟังก์ชัน `buildProjectFlexBubble_()` ใน `Code.gs` (เพิ่ม/ลบ field, เปลี่ยนสี, เปลี่ยน layout) — อ้างอิง syntax ได้จาก [LINE Flex Message Simulator](https://developers.line.biz/flex-simulator/)
- ปรับจำนวนชื่อสูงสุดต่อการ์ดได้ที่ตัวแปร `FLEX_MAX_NAMES_PER_SECTION` (ค่าเริ่มต้น 8)
- ส่วน "แผนก/ตำแหน่งที่มีปัญหา" ปรับได้ที่ฟังก์ชัน `appendDepartmentIssueLines_()` (เช่นเปลี่ยนจำนวนแผนกสูงสุดที่แสดงจาก 6 เป็นค่าอื่น หรือเปลี่ยนเกณฑ์ "ขาดครบทั้งแผนก")
- กราฟแท่งเปรียบเทียบโครงการ (ในการ์ดสรุปภาพรวม) ปรับได้ที่ `buildProjectSummaryBubble_()` — เปลี่ยนจำนวน Top N จาก 5 ได้ที่ `.slice(0, 5)`

### ถ้า Execution log ตัด JSON ทิ้ง (ยาวเกิน)

รันฟังก์ชัน **`previewProjectAttendanceReportToDoc`** แทน — จะสร้าง Google Doc ใหม่ 1 ไฟล์ เขียน JSON แบบเต็มไม่ตัดทอนลงไป แล้ว log ลิงก์ไฟล์ให้ใน Execution log (ครั้งแรกที่รันจะมีหน้าต่างขอ authorize สิทธิ์ Google Docs เพิ่ม เพราะเป็นการใช้ service ใหม่ — กดอนุญาตได้เลย) เปิดลิงก์แล้วคัดลอก JSON ไปวางที่ [LINE Flex Message Simulator](https://developers.line.biz/flex-simulator/) ได้แบบครบถ้วน

### วิธีทดสอบที่น่าเชื่อถือที่สุด: ส่งจริงไปเลย

แทนที่จะเดาว่า JSON ถูกไหมจาก simulator รันฟังก์ชัน **`testSendFirstProjectFlexCard`** เพื่อส่ง Flex Carousel ชุดแรกเข้ากลุ่มไลน์จริง (ไม่ส่งข้อความสรุป) — ถ้า JSON มีปัญหาจริง LINE server จะตอบ error message ที่ชัดเจนกลับมาใน Execution log ทันที น่าเชื่อถือกว่าการอ่าน log ที่อาจถูกตัดทิ้ง

## การปรับแต่งรายงาน

ฟังก์ชัน `computeDailyDashboardData_()` ใน `Code.gs` เป็นจุดที่กำหนดว่าจะคำนวณตัวชี้วัดอะไรบ้าง (อ้างอิงตรรกะเดียวกับ Dashboard จริงใน `src/components/ManpowerDashboard.tsx`) ส่วนหน้าตาการ์ดปรับได้ที่ `buildDailyDashboardFlexMessage_()` ตอนนี้มีตัวชี้วัดดังนี้:

- จำนวนพนักงานที่ `สถานะพนักงาน === "ทำงาน"`
- มา/ขาด/ลาวันนี้ (อ้างอิงจาก `attendance/{YYYY-MM-DD}`)
- จำนวนเคสติดตาม (`employee_follow_ups`) ที่ยังไม่ปิด
- **เพศ** (ชาย/หญิง/ไม่ระบุ — ใช้ field `gender`/`เพศ` หรืออนุมานจากคำนำหน้าชื่อถ้าไม่มี)
- **สัดส่วนกำลังคน** (DC ไทย/ต่างชาติ และ Supply ไทย/ต่างชาติ — คำนวณจาก `employee_type` + `สถานะกลุ่มงาน` + `สัญชาติ`)

ดูตัวอย่างหน้าตาการ์ดได้ในหัวข้อ "รายงานที่ 1" ด้านบน ถ้าอยากได้เวอร์ชัน **text ล้วน** (ไม่ใช่การ์ด) ยังเรียกดูได้จาก `buildDailyReportMessage_()` / `previewDailyReportMessage()` เหมือนเดิม

ส่วนรายงานแยกตามโครงการ (ดูหัวข้อ "รายงานที่ 2" ด้านบน) คำนวณข้อมูลใน `computeProjectAttendanceData_()` แล้วแสดงผ่าน Flex Carousel (`buildProjectAttendanceFlexMessages_()` / `buildProjectFlexBubble_()`)

สามารถเพิ่มตัวชี้วัดอื่นได้ เช่น OT เกินเพดาน, เคส risk ใหม่ ฯลฯ โดยเรียก `firestoreListDocuments_("CMG-HR-Database/root/<collection>")` เพิ่ม แล้วกรอง/นับตามต้องการ — ควรตรวจชื่อฟิลด์จริงใน Firestore Console ก่อน เพราะบาง field เป็นภาษาไทย (เช่น `สถานะพนักงาน`)

## แก้ปัญหา `Invalid argument: key`

ถ้ารัน `previewDailyReportMessage` หรือฟังก์ชันที่ดึง Firestore แล้วเจอ error:

```
Exception: Invalid argument: key
getFirestoreAccessToken_ @ Code.gs:...
```

แปลว่าค่า `SERVICE_ACCOUNT_PRIVATE_KEY` ใน Script Properties มีรูปแบบไม่ถูกต้อง (ไม่ใช่ PEM format) วิธีแก้:

### 1. รันฟังก์ชันตรวจสอบในตัว

ใน Apps Script editor เลือกฟังก์ชัน **`debugCheckServiceAccountKey`** จาก dropdown > กด **Run** แล้วดูผลใน **Execution log** (View > Logs) จะบอกว่าปัญหาคืออะไร (ไม่เปิดเผยคีย์เต็ม ปลอดภัย)

### 2. วิธีคัดลอก private key ที่ถูกต้อง

เปิดไฟล์ JSON ของ Service Account ด้วย **Notepad หรือ text editor ธรรมดา** (ห้ามเปิดด้วยโปรแกรมที่ "จัดรูปแบบ JSON สวยๆ" เช่นบางเว็บ JSON formatter เพราะอาจแปลง `\n` เป็น newline จริงแบบผิดที่) จะเห็นบรรทัดประมาณนี้:

```json
"private_key": "-----BEGIN PRIVATE KEY-----\nMIIEvQIBADANBgkqhkiG9w0BAQEFAASCBKcwggSjAgEAAoIBAQ...\n-----END PRIVATE KEY-----\n",
```

- คัดลอก**เฉพาะข้อความในเครื่องหมายคำพูด** (ไม่รวม `"private_key":` และไม่รวมเครื่องหมาย `"` หัวท้าย)
- ต้องได้ค่าที่ขึ้นต้นด้วย `-----BEGIN PRIVATE KEY-----` และมี `\n` เป็นตัวอักษร (backslash ตามด้วยตัว n) คั่นอยู่ระหว่างบรรทัด ไม่ใช่การขึ้นบรรทัดใหม่จริง
- วางค่านี้ลงใน Script Properties ช่อง `SERVICE_ACCOUNT_PRIVATE_KEY` ทั้งก้อนแบบไม่ตัดทอน

โค้ดในไฟล์นี้ (ฟังก์ชัน `normalizePrivateKey_`) รองรับทั้งกรณีที่วางมาเป็น `\n` (backslash-n) และกรณีที่วางมาเป็น newline จริงอยู่แล้ว รวมถึงตัดเครื่องหมายคำพูดที่อาจติดมาด้วยให้อัตโนมัติ — ถ้ายังไม่ผ่านหลังรัน `debugCheckServiceAccountKey` ให้คัดลอกค่าจากไฟล์ JSON มาวางใหม่ทั้งหมด (บางครั้งการ copy ผ่านหลายแอปทำให้อักขระพิเศษเพี้ยน)

## ข้อจำกัดของแนวทางนี้

- เป็น **scheduled report** (ตามรอบเวลา) ไม่ใช่ real-time — ถ้าต้องการแจ้งทันทีที่มีเหตุการณ์เกิดขึ้น (เช่น เคส risk ใหม่) ต้องใช้ Firebase Cloud Functions + Firestore Trigger แทน
- ขนาดข้อมูลที่ Apps Script ดึงจาก Firestore REST API ต่อครั้งมีจำกัด (execution time 6 นาที/ครั้งสำหรับบัญชีฟรี) — ถ้า collection มีข้อมูลหลักหมื่น-แสน rows ควรใช้ query filter เพิ่มเติมแทนการดึงทั้ง collection
  - ส่วน OT burden + แนวโน้ม 7 วัน เพิ่มการเรียก Firestore อีกประมาณ **วันที่ผ่านมาแล้วของเดือน + 7 ครั้ง** ต่อการรัน `sendDailyDashboardReport` 1 ครั้ง (เช่นวันที่ 20 ของเดือน จะยิง `overtime/{date}` ~20 ครั้ง + `attendance/{date}` อีก 7 ครั้ง) ยังอยู่ในขอบเขตปกติ ไม่น่ากระทบ execution time แต่ถ้า collection เริ่มช้าในอนาคตให้มาดูจุดนี้ก่อน
- เพดาน OT ที่ใช้ไฮไลต์สี (`OT_MONTHLY_TIERS` ใน `Code.gs`) เป็นค่าที่ **copy มาจาก default ของเว็บแอป** (`src/config/overtimeLimits.ts`) ไว้ ณ ตอนที่เขียนโค้ด — ถ้าแอดมินไปแก้ตัวเลขเพดานในหน้าเว็บ (Firestore: `settings/overtime_limits`) ภายหลัง ค่านี้จะ**ไม่อัปเดตตามอัตโนมัติ** ต้องมาแก้ตัวเลขใน `Code.gs` เองให้ตรงกัน
- Private key ของ Service Account เป็นความลับสำคัญ ห้าม commit เข้า git หรือแชร์ที่ใดๆ
